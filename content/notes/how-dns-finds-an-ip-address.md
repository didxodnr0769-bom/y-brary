브라우저 주소창에 `mysite.com`을 입력하면 어떻게 해당 사이트를 찾아갈까? 사람이 기억하기 쉬운 도메인 이름으로 접속하려면, 먼저 통신에 사용할 IP 주소를 알아야 한다. 이때 도메인 이름에 해당하는 주소를 찾는 체계가 **DNS**다.

## 1. 주소에서 도메인을 확인한다

다음과 같은 주소를 입력했다고 해보자.

```text
https://mysite.com/products
        └────┬────┘
          도메인 이름
```

`https://`는 통신 방식이고, `mysite.com`은 찾아갈 사이트의 이름이다. `/products`는 해당 사이트에 요청할 경로다. DNS 조회에서는 이 중 `mysite.com`에 해당하는 IP 주소를 찾는다.

## 2. 누가 IP 주소를 찾아줄까?

브라우저가 모든 도메인의 IP 주소를 미리 알고 있는 것은 아니다. 보통은 **DNS 리졸버**에 주소를 찾아달라고 요청한다. 리졸버는 사용자를 대신해 필요한 곳에 물어보고 그 결과를 돌려준다.

![사용자가 주소를 물어보면 리졸버가 여러 곳에 정보를 확인하고 찾은 주소를 돌려주는 모습을 비유한 그림](/images/notes/dns/dns-lookup.webp)

먼저 브라우저나 운영체제, 리졸버에 이전에 찾아둔 결과가 있는지 확인할 수 있다. 아직 유효한 결과가 있다면 이를 사용해 조회 과정을 줄인다. 이렇게 잠시 저장해 둔 정보를 **캐시**라고 한다.

## 3. 리졸버는 어디에 물어볼까?

필요한 정보가 캐시에 없다고 가정하면, 리졸버는 위에서부터 안내를 받으며 찾아간다.

```text
브라우저: mysite.com의 IP 주소를 찾아줘
    ↓
DNS 리졸버
    │
    ├─ 루트 DNS 서버에 질문
    │  → “.com을 담당하는 곳에 물어보세요.”
    │
    ├─ .com을 담당하는 DNS 서버에 질문
    │  → “mysite.com의 네임서버에 물어보세요.”
    │
    └─ mysite.com의 네임서버에 질문
       → “mysite.com의 IP 주소는 이 주소입니다.”
    ↓
찾은 IP 주소를 브라우저에 전달
```

루트 DNS 서버가 모든 도메인의 IP 주소를 외우고 있는 것은 아니다. 다음에 어디에 물어볼지 안내하는 출발점이다. 리졸버에는 출발점이 되는 루트 서버의 주소 정보가 미리 준비되어 있다.

실제로는 매번 이 과정을 처음부터 반복하지 않는다. 리졸버가 네임서버나 IP 주소를 이미 기억하고 있다면 중간 단계를 건너뛸 수 있다.

## 4. 도메인의 네임서버란?

**네임서버는 도메인이 어디로 연결되는지 알려주는 곳이다.** 도메인을 등록할 때 이 도메인의 정보를 어느 네임서버에서 관리할지 지정한다.

`mysite.com`을 예로 들면, `.com`을 담당하는 DNS 서버가 `mysite.com`의 네임서버가 어디인지 리졸버에 안내한다. 리졸버는 그 네임서버에 다시 물어봐서 연결에 필요한 정보를 얻는다.

도메인을 구입한 곳, 네임서버를 관리하는 곳, 실제 사이트를 운영하는 플랫폼은 서로 같을 수도 있고 다를 수도 있다.

## 5. 사이트를 다른 플랫폼으로 옮기면?

`mysite.com`이 A 플랫폼을 가리키다가 B 플랫폼을 가리키도록 설정을 바꿨다고 해보자.

```text
변경 전: mysite.com → A 플랫폼

변경 직후:
이전 주소를 기억하는 곳 → A 플랫폼
새 주소를 확인한 곳     → B 플랫폼

시간이 지난 뒤: 새 주소를 다시 확인해 B 플랫폼으로 연결
```

누군가 이전 주소를 캐시에 저장해 두었다면, 변경 직후에도 잠시 A 플랫폼으로 접속할 수 있다. 반면 새 주소를 조회한 사람은 B 플랫폼으로 접속한다. 따라서 모든 사람의 연결이 같은 순간에 바뀌지는 않는다.

DNS 정보에는 보통 **얼마나 오래 저장할 수 있는지**를 나타내는 TTL이라는 시간이 있다. 예를 들어 기존 정보의 TTL이 1시간이고 리졸버가 변경 직전에 그 정보를 저장했다면, 해당 리졸버는 약 1시간 동안 이전 답을 사용할 수 있다. 이미 저장한 지 시간이 지났다면 더 빨리 새 정보를 확인한다. 실제 전환 시간은 설정과 캐시 상태에 따라 달라진다.

그래서 이전할 때는 B 플랫폼을 먼저 준비하고, 가능하다면 A 플랫폼도 한동안 유지한다. 전환 중 어느 쪽으로 연결되더라도 사이트를 이용할 수 있도록 하기 위해서다.

## 6. 플랫폼을 옮기면 네임서버도 바꿔야 할까?

꼭 그렇지는 않다. 현재 네임서버에서 B 플랫폼으로 연결하는 설정을 할 수 있다면, **네임서버는 그대로 두고 연결 정보만 바꿀 수 있다.**

```text
변경 전: 기존 네임서버 → A 플랫폼 안내
변경 후: 기존 네임서버 → B 플랫폼 안내
```

반대로 새 서비스가 자체 네임서버 사용을 요구하거나, 도메인 연결 정보를 관리하는 곳 자체를 옮기고 싶다면 네임서버를 바꿀 수 있다. 이때는 새 네임서버에 웹사이트 연결 정보뿐 아니라 사용 중인 이메일 관련 설정 등도 옮겨야 한다.

네임서버를 바꾸는 경우에도 이전 정보가 한동안 캐시에 남을 수 있다. 일부는 기존 네임서버를, 다른 일부는 새 네임서버를 참고할 수 있으므로 양쪽 설정을 신중하게 준비해야 한다.

## 7. IP 주소를 찾은 다음에는?

브라우저는 찾은 주소를 이용해 서버에 연결하고 페이지를 요청한다. 응답으로 HTML 등을 받으면 화면을 만들기 시작한다. 그 이후의 과정은 [브라우저는 어떻게 화면을 그릴까?](/notes/how-browser-renders-a-page)에서 이어서 살펴볼 수 있다.

```text
도메인 입력 → DNS로 주소 찾기 → 서버에 페이지 요청 → 화면 그리기
```

하나의 도메인에 여러 IP 주소가 연결될 수도 있으며, 찾은 주소는 실제 원본 서버 앞에서 요청을 받는 서버의 주소일 수도 있다.
