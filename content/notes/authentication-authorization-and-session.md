로그인한 사용자라면 모든 글을 수정할 수 있을까?

일반적으로는 그렇지 않다. 로그인을 했더라도 다른 사람이 작성한 글을 수정할 권한까지 생기지는 않는다.

이 차이를 설명하는 개념이 **인증**과 **인가**다.

## 1. 인증은 누구인지 확인하는 일

**인증(Authentication)은** 요청한 주체가 자신이 주장하는 대상이 맞는지 확인하는 과정이다.

아이디와 비밀번호로 로그인하는 상황을 생각하면 쉽다. 아이디를 입력하는 것만으로는 해당 계정의 사용자라고 믿을 수 없다. 서버는 비밀번호 등을 검증해 그 계정의 사용자가 맞는지 확인한다.

> 인증이 답하는 질문: “누구의 요청인가?”

여기서 확인하는 것은 서비스 안의 계정이다. 로그인이 반드시 사용자의 실제 이름이나 현실의 신원까지 확인한다는 뜻은 아니다.

## 2. 인가는 그 일을 해도 되는지 판단하는 일

**인가(Authorization)는** 요청한 작업을 수행할 권한이 있는지 판단하는 과정이다.

사용자를 확인한 뒤에도, 그 사용자가 어떤 글을 읽거나 수정할 수 있는지는 따로 검사해야 한다.

> 인가가 답하는 질문: “이 요청을 허용해도 되는가?”

개인 기록 사이트에 로그인과 글 수정 기능을 붙인다고 가정해보자. 글은 작성자만 수정할 수 있도록 정했다.

| 상황 | 확인할 내용 | 구분 |
| --- | --- | --- |
| 계정에 로그인한다 | 해당 계정의 사용자가 맞는가? | 인증 |
| 내 글을 수정한다 | 이 사용자에게 이 글의 수정 권한이 있는가? | 인가 |
| 다른 사람의 글을 수정하려 한다 | 수정 권한이 없다면 요청을 거절한다. | 인가 |

두 사람이 모두 로그인에 성공해도 서로의 글을 수정할 수 있는 것은 아니다. **인증에 성공했다는 사실이 모든 권한을 준다는 뜻은 아니다.**

## 3. 로그인 후에는 사용자를 어떻게 알아볼까?

로그인할 때는 아이디와 비밀번호를 제출한다. 그렇다면 다음 페이지를 열거나 글을 수정할 때도 매번 같은 정보를 보내야 할까?

여기서는 **서버가 세션을 저장하고, 브라우저가 세션 ID를 쿠키로 보내는 방식**을 살펴본다. 로그인 상태를 유지하는 여러 방식 중 하나다.

![세션 로그인 흐름. 서버가 로그인 정보를 검증하고 세션을 저장한다. 브라우저는 쿠키에 세션 ID를 저장해 후속 요청에 보내며, 서버는 유효한 세션으로 사용자를 확인한 뒤 글 수정 권한을 판단한다.](/images/notes/authentication/session-login-flow.webp)

### 첫째, 서버가 로그인 정보를 검증한다

브라우저가 보낸 로그인 정보를 서버가 확인한다. 검증에 성공하면 해당 계정의 사용자로 인증한다.

예를 들어 서버가 확인한 계정의 사용자 ID가 `42`라고 하자.

### 둘째, 서버가 세션을 만든다

서버는 로그인 상태를 저장하고, 그 상태를 찾을 수 있는 **세션 ID**를 발급한다. 세션 ID는 다른 사람이 쉽게 예측할 수 없어야 한다.

세션 저장소에는 개념적으로 다음과 같은 연결이 만들어진다.

| 항목 | 역할 |
| --- | --- |
| 세션 ID | 저장된 세션을 찾는 식별자 |
| 사용자 ID: 42 | 이 세션으로 확인할 사용자 |
| 만료 시각 등 | 세션이 유효한지 판단할 정보 |

서버는 응답을 통해 브라우저가 세션 ID를 쿠키에 저장하도록 한다.

### 셋째, 브라우저가 쿠키를 함께 보낸다

이후 브라우저는 쿠키의 전송 조건에 맞는 요청에 해당 쿠키를 함께 보낸다.

서버는 쿠키에 담긴 세션 ID로 세션을 조회한다. 유효한 세션이 사용자 `42`와 연결돼 있다면, 그 요청을 42번 사용자의 요청으로 처리한다.

즉, 다음 요청에서는 아이디와 비밀번호를 다시 제출하는 대신 **유효한 세션을 통해 로그인 상태를 확인**한다. 세션이 없거나 만료됐다면 로그인 상태로 인정하지 않는다.

### 넷째, 요청한 작업의 권한을 검사한다

42번 사용자가 글 수정을 요청했다고 하자. 서버는 사용자를 확인한 다음, 해당 글의 작성자가 42번인지 검사한다.

작성자만 수정할 수 있다는 정책이라면, 작성자가 같은 경우에만 수정을 허용한다.

```text
글 수정 요청
    ↓
세션으로 사용자 확인
“42번 사용자의 요청이다.”
    ↓
수정 권한 확인
“이 글의 작성자가 42번인가?”
    ↓
맞으면 수정 허용
아니면 수정 거절
```

이 흐름에서 **사용자를 확인하는 부분은 인증**, **수정 권한을 판단하는 부분은 인가**다.

## 4. 쿠키와 세션은 역할이 다르다

쿠키와 세션은 함께 쓰이기 때문에 혼동하기 쉽다. 앞의 예시에서는 다음처럼 역할을 나눈다.

| 개념 | 역할 |
| --- | --- |
| 쿠키 | 브라우저가 값을 저장하고, 조건에 맞는 요청에 실어 보내는 수단 |
| 세션 | 서버가 관리하는 사용자와의 상호작용 상태. 여기서는 로그인 상태를 담는다. |
| 세션 ID | 서버의 세션을 찾기 위해 브라우저가 전달하는 식별자 |

**쿠키는 전달 수단이고, 세션은 서버가 관리하는 상태**라고 구분하면 이해하기 쉽다.

이 방식에서는 브라우저의 쿠키에 사용자 정보 전체나 비밀번호를 담을 필요가 없다. 세션 ID를 보내면 서버가 그에 연결된 정보를 찾는다.

다만 세션 ID도 중요한 인증 정보다. 비밀번호가 아니더라도 유출되면 다른 사람이 로그인 상태를 악용할 수 있으므로 안전하게 다뤄야 한다.

## 5. 권한 검사는 서버에서 해야 한다

화면에서 글 수정 버튼을 숨기는 것만으로는 권한 검사가 끝나지 않는다. 사용자가 버튼을 누르지 않고 서버에 수정 요청을 직접 보낼 수도 있기 때문이다.

따라서 **서버는 보호할 데이터나 기능에 대한 요청마다 권한을 검사**해야 한다. 요청에 사용자 ID가 들어 있다고 해서 그대로 믿어서도 안 된다. 검증된 세션 등으로 요청한 사용자를 확인한 뒤 권한을 판단해야 한다.

또한 모든 접근에 로그인이 필요한 것은 아니다. 공개 글은 누구나 읽을 수 있고, 수정은 작성자에게만 허용할 수 있다.

“누구나 읽기 허용”도 하나의 접근 정책이다. 인가는 로그인 여부만 확인하는 일이 아니라, **해당 요청에 적용할 정책에 따라 허용 여부를 결정하는 일**이다.

## 6. 두 가지 질문으로 구분하기

인증과 인가가 헷갈린다면, 지금 무엇을 확인하고 있는지 생각해보면 된다.

- **인증:** 이 요청은 누구의 요청인가?
- **인가:** 이 사용자에게 이 작업을 허용해도 되는가?

로그인은 인증의 대표적인 예다. 이후에는 세션 같은 수단으로 사용자를 확인할 수 있다. 그리고 보호할 작업을 처리하기 전에, 그 사용자에게 필요한 권한이 있는지 따로 검사한다.

세션과 쿠키를 구분할 때도 역할을 떠올리면 된다. 이 글의 예시에서 서버는 세션으로 로그인 상태를 관리하고, 브라우저는 쿠키에 담긴 세션 ID를 보내 그 상태를 확인받는다.
