S3는 파일을 저장하는 서비스라고 하는데, React로 만든 웹사이트를 올리는 데도 사용한다. 그렇다면 S3가 웹사이트의 코드를 실행해주는 것일까?

이 질문을 이해하려면 먼저 S3에 무엇을 저장하고, 저장한 파일을 누가 사용하는지 구분해야 한다.

## 1. S3는 무엇을 저장하는 서비스일까?

**Amazon S3(Simple Storage Service)는** AWS가 제공하는 객체 스토리지다. 이미지, 문서, 영상, 백업 파일 같은 데이터를 저장하고 필요할 때 가져올 수 있다.

예를 들어 게시글에 첨부할 이미지나 사용자가 업로드한 PDF를 보관할 수 있다. 웹사이트를 구성하는 HTML·CSS·JavaScript 파일도 저장할 수 있다.

여기서 기본적으로 알아둘 용어는 **버킷, 객체, 키** 세 가지다.

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| 버킷(Bucket) | 객체를 담는 저장 공간 | `my-learning-assets` |
| 객체(Object) | 저장한 데이터와 그 데이터를 설명하는 메타데이터 | 이미지 데이터와 파일 형식 등의 정보 |
| 키(Key) | 버킷 안에서 객체를 구분하는 이름 | `notes/image.webp` |

![버킷 안에 이미지·문서·영상 객체가 들어 있다. 이미지 객체는 파일 데이터와 메타데이터로 구성되며, notes/image.webp라는 키로 찾는다.](/images/notes/s3/s3-bucket-object-key.webp)

버킷 하나에 이미지를 저장했다면, **어느 버킷의 어떤 키인지**를 이용해 그 이미지를 찾을 수 있다.

이때 키는 비밀번호나 인증 키가 아니다. `notes/image.webp`처럼 객체를 식별하는 이름이다.

일반적인 S3 버킷에서는 `/`를 넣어 폴더처럼 구분해 보여줄 수 있다. 하지만 `notes/image.webp` 전체가 하나의 객체 키라는 점을 기억하면 된다.

## 2. React 빌드 결과물을 올리면 어떻게 웹사이트가 될까?

핵심은 **S3가 파일을 제공하고, 브라우저가 JavaScript를 실행한다**는 점이다.

Vite로 만든 React 앱을 빌드하면 JSX·TypeScript 등을 브라우저가 사용할 수 있는 JavaScript로 변환하고 필요한 파일을 묶는다. 배포 결과물에는 HTML, CSS, JavaScript와 이미지 등이 포함된다.

예를 들면 다음과 같다. 파일 이름은 빌드 설정에 따라 달라질 수 있다.

```text
dist/
├─ index.html
└─ assets/
   ├─ index-abc123.js
   ├─ index-def456.css
   └─ image.webp
```

이 파일들을 S3에 올리면 각각 하나의 객체로 저장된다. 배포 구조에 맞게 접근 권한과 기본 문서, URL 경로를 설정하면 웹사이트의 파일로 제공할 수 있다.

![React 앱을 빌드해 HTML·CSS·JavaScript 파일을 만든다. 결과물을 S3에 저장하고, 브라우저가 파일을 내려받아 JavaScript를 실행하며 화면을 구성한다.](/images/notes/s3/s3-static-hosting-flow.webp)

사용자가 사이트에 접속하면 브라우저는 먼저 HTML을 받는다. 이어서 HTML에 연결된 JavaScript와 CSS 등을 요청한다.

브라우저는 받은 JavaScript를 실행한다. 그 코드에 포함된 React와 앱의 로직이 화면을 구성하고 사용자 입력을 처리한다.

| 구성 요소 | 담당하는 일 |
| --- | --- |
| S3 | 빌드된 파일을 저장하고 요청에 따라 제공한다. |
| 브라우저 | JavaScript를 실행하고 화면을 표시한다. |
| 별도 백엔드 API | 필요한 경우 인증·인가나 데이터 저장 같은 서버 작업을 처리한다. |

이 설명은 브라우저에서 실행되는 React 앱의 정적 빌드를 기준으로 한다. S3에 소스 파일을 올렸다는 이유만으로 서버 프로그램이 실행되는 것은 아니다.

## 3. 정적 사이트에서도 화면이 바뀔 수 있다

정적 사이트라고 하면 내용이 움직이지 않는 화면을 떠올리기 쉽다.

하지만 여기서 **정적이라는 말은 미리 준비된 파일을 제공한다는 의미**다. 브라우저에서 화면이 바뀌거나 버튼이 동작할 수 없다는 뜻은 아니다.

브라우저가 받은 JavaScript로 검색 결과를 좁히거나, 메뉴를 열거나, 페이지를 전환할 수 있다. 별도 API를 호출해서 새로운 데이터를 가져올 수도 있다.

다만 API가 요청을 받아 처리하는 일은 그 API를 실행하는 서버나 서비스가 담당한다. 정적 파일을 보관하는 S3의 역할과 구분해야 한다.

## 4. Next.js 프로젝트도 S3에 올릴 수 있을까?

**정적 파일로 내보낼 수 있는 Next.js 프로젝트라면 가능하다.**

Next.js에는 정적 내보내기(Static Export) 기능이 있다. 다음은 이를 사용하는 설정 예시다.

```js
// next.config.mjs
const nextConfig = {
  output: "export",
};

export default nextConfig;
```

`next build`를 실행하면 기본적으로 `out/` 폴더에 HTML·CSS·JavaScript 등이 만들어진다. 이를 S3에 저장해 제공할 수 있다. 생성된 파일과 실제 URL을 연결하는 경로 설정도 필요하다.

판단할 때 중요한 질문은 **“이 코드를 언제 실행해야 하는가?”다.**

| 실행 시점 | 예시 | S3 정적 호스팅과의 관계 |
| --- | --- | --- |
| 빌드할 때 | 글을 읽어 페이지를 미리 생성 | 결과물을 정적 파일로 제공할 수 있다. |
| 사용자의 브라우저에서 | 버튼 동작, 검색, 별도 API 호출 | 내려받은 JavaScript로 처리할 수 있다. |
| 사용자 요청을 받을 때 서버에서 | 요청별 SSR, Server Actions | 해당 코드를 실행할 별도 환경이 필요하다. |

Server Component라는 이름만 보고 정적 배포가 불가능하다고 판단해서는 안 된다. 빌드할 때 실행해 결과를 미리 만들 수 있는 Server Component는 정적 내보내기에서도 사용할 수 있다.

반면 요청의 쿠키를 읽어 사용자별 HTML을 만들거나 Server Actions를 실행해야 한다면, S3 정적 호스팅만으로는 처리할 수 없다. ISR이나 기본 이미지 최적화처럼 정적 내보내기에서 지원하지 않는 기능도 있으므로 사용하는 기능을 확인해야 한다.

## 5. 구글 드라이브 대신 개인 저장소로 써도 될까?

사진, 문서, 영상, 백업 파일을 개인적으로 보관하는 용도로도 사용할 수 있다. 파일을 저장하기 위해 반드시 별도의 앱을 개발해야 하는 것은 아니다. AWS 관리 화면에서도 파일을 올리고 내려받을 수 있다.

다만 구글 드라이브와 S3는 기본적으로 제공하는 사용 경험이 다르다.

| 구분 | 구글 드라이브 | S3 |
| --- | --- | --- |
| 기본 성격 | 사람이 파일을 관리하는 완성된 서비스 | 앱이나 서비스가 활용할 수 있는 저장 기반 |
| 파일 관리 | 드라이브 앱이나 웹 화면을 사용 | AWS 관리 화면, CLI, API 등으로 관리 |
| 직접 만드는 기능 | 제공되는 기능을 중심으로 사용 | 별도 화면과 서버를 연결해 저장·공유 흐름을 구성할 수 있음 |

S3를 이용해 나만의 드라이브를 만든다면, 파일 목록과 업로드 버튼은 웹 화면에서 제공하고 실제 파일은 S3에 저장하는 구조로 나눌 수 있다.

로그인한 사용자가 어떤 파일을 볼 수 있는지는 백엔드에서 확인할 수 있다. 앞서 살펴본 인증과 인가가 파일 저장 서비스에도 연결되는 것이다.

## 6. 저장한 파일은 누구나 볼 수 있을까?

**S3에 업로드했다고 자동으로 모든 사람에게 공개되는 것은 아니다.** 기본적으로 버킷과 객체는 비공개이며, 접근을 허용하려면 그에 맞는 권한이 필요하다.

예를 들어 개인 문서가 있는 버킷은 비공개로 유지하고, 서비스에서 사용자의 권한을 확인한 뒤 특정 파일에 접근할 수 있게 할 수 있다.

이때 활용할 수 있는 기능 중 하나가 **미리 서명된 URL(Presigned URL)이다.** 특정 객체에 대한 업로드나 다운로드를 일정 시간 허용하는 주소를 만들어 전달하는 방식이다.

이 주소를 가진 사람은 허용된 범위에서 파일에 접근할 수 있으므로, 주소 자체도 접근 권한을 가진 정보로 다뤄야 한다.

## 7. 저장소로 사용할 때 구분할 점

S3의 비용은 저장 용량만으로 결정되지 않는다. 요청 횟수, 외부로 전송하는 데이터, 사용하는 저장 클래스와 기능 등에 따라서도 달라진다.

파일을 오래 보관하는 경우와 많은 사용자가 자주 내려받는 경우는 사용 형태가 다르다. 실제 비용을 비교하려면 어느 리전에 얼마나 저장하고, 얼마나 요청하고 전송하는지 함께 봐야 한다.

또한 여기서 설명한 S3의 역할은 **파일을 객체로 저장하는 것**이다. JSON이나 CSV 파일도 보관할 수 있지만, 그것만으로 사용자나 게시글의 정보를 조건별로 검색하고 개별 항목을 자주 수정하는 일반적인 데이터베이스 기능이 생기지는 않는다.

서비스에서는 사용자 정보나 파일 소유자·객체 키 등의 목록을 데이터베이스에 두고, 실제 이미지·문서 파일은 S3에 두는 식으로 역할을 나눌 수 있다.

S3를 이해할 때는 세 가지를 구분하면 된다. **무엇을 저장하는지**, **누가 그 파일을 실행하거나 사용하는지**, **누구에게 접근을 허용하는지**다. 이 구분을 잡으면 파일 보관과 웹사이트 정적 배포를 같은 저장 서비스로 처리할 수 있는 이유도 이해할 수 있다.
